# Platform administration

The administration API uses a separate `ADMIN` capability enforced by the server. It provides moderation, account suspension, session revocation, platform statistics, append-only audit history, and durable-job monitoring. It does not custody funds, change eligibility or published allocations, replace Merkle roots, or sign transactions.

## Bootstrap and authentication

Configure `ADMIN_WALLETS` as a comma-separated list of trusted operator EVM addresses. Empty is the default and disables all administrative access. The configuration accepts at most 20 nonzero, unique addresses. No public endpoint grants an administrator role; a user cannot acquire the role through account creation, campaign ownership, a request field, or a header.

```dotenv
# Example only; replace with your verified operator wallet.
ADMIN_WALLETS=0x1111111111111111111111111111111111111111
```

Sign in with the existing wallet challenge/verification flow. Every admin request requires the session cookie, an allowlisted wallet, and a session created less than 15 minutes ago. EIP-1271 wallet validation continues to apply. Expired administrative freshness returns `403 ADMIN_REAUTH_REQUIRED`; sign a new challenge to obtain a fresh session. The ordinary user session can still be valid after this administrative window expires.

Admin mutations require an exact allowed `Origin`, `X-CSRF-Token`, and `Idempotency-Key`. Their transactions recheck and lock the session before changes or cached retries are accepted. Reasons are mandatory, nonblank, and at most 2,000 characters. Version checks reject stale changes. Mutation responses and audit records commit atomically with the action.

Apply migration `0005_platform_administration.sql` before rolling out the API/worker version. Inject the same allowlist into all API replicas; changing it requires a controlled configuration rollout. For urgent removal, update every replica and revoke the affected sessions through the restricted database incident procedure. Use operator wallets with an appropriate signing policy; wallet/session compromise grants the configured administrative capability.

## Endpoints

| Method | Path under `/v1` | Purpose |
| --- | --- | --- |
| GET | `/admin/me` | Administrator identity, permissions, and reauthentication deadline |
| GET | `/admin/stats` | Platform counters, job-state counts, and indexer health |
| GET | `/admin/campaigns` | All campaign metadata, including drafts, with moderation state |
| POST | `/admin/campaigns/{id}/moderation` | Hide or restore campaign discovery and new registration |
| GET | `/admin/users` | User status and administration version without session credentials |
| POST | `/admin/users/{id}/suspension` | Suspend or restore an account |
| POST | `/admin/users/{id}/revoke-sessions` | Revoke current sessions and require a new login |
| GET | `/admin/audit-logs` | Read append-only audit records |
| GET | `/admin/jobs` | Monitor allocation jobs, attempts, lease, and safe error code |

These endpoints are documented with typed request/response schemas in [openapi.json](openapi.json). List endpoints return `items` and an opaque `next_cursor`; use `limit` (1–100, default 25) and `cursor` to page newest first. Do not construct cursors yourself. Concurrent new inserts appear when refreshing the first page rather than being injected into an existing pagination traversal.

Supported filters:

- Campaigns: `hidden=true|false`.
- Users: `wallet` and `suspended=true|false`.
- Audit logs: `campaign_id` and `actor_id`.
- Jobs: `campaign_id` and `status=PENDING|RUNNING|FAILED|SUCCEEDED`.

Unknown query fields and filters belonging to another listing are rejected. Account/session secrets, saved sign-in signatures, private evidence images, and encrypted raffle seeds are not exposed by these endpoints. Audit metadata is generated by the relevant business operation; it is not a raw HTTP payload dump.

## Campaign moderation

```json
{
  "expected_version": 0,
  "hidden": true,
  "reason": "Investigating a community report."
}
```

Use the version returned under `moderation.version` in the admin campaign listing. This is separate from the creator's business/configuration version. Hiding a campaign:

- Removes it from public listings, including previously cached listings through a database-backed revision.
- Returns 404 for public detail access by visitors and nonparticipants.
- Blocks new registration while the campaign otherwise remains open.
- Preserves detail access for the creator and already registered participants.
- Preserves existing evidence submission/review, finalization, public distribution artifacts/proofs, and onchain claim/refund rights.

Moderation does not change `listed`, activation, chain state, deadlines, locked rules, allocations, or ownership. Therefore a later activation/indexer event cannot silently undo a hidden flag. Restoring uses `hidden:false` with the current moderation version and a reason. It does not turn a private draft into a publicly activated campaign.

## Account suspension and session revocation

```json
{
  "expected_version": 0,
  "suspended": true,
  "reason": "Investigating repeated abuse."
}
```

Use the `version` from the admin user listing. Suspension increments the administration version and revokes current, unexpired sessions in the same transaction. Suspended users cannot authenticate or perform authenticated operations. User locks serialize suspension with login/session issuance and transactional business writes. Requests authenticated before standalone session revocation can already be in flight; revocation governs subsequent authentication, while suspension also fences transactional writes through the user lock.

Restoring uses `suspended:false` and the latest version. Old revoked sessions are not restored; the user must log in again. Suspension does not automatically hide the user's campaigns, change eligibility, or confiscate rewards. Use campaign moderation separately when needed. Claim artifacts remain public and contracts continue enforcing their own claim rights.

Standalone revocation accepts:

```json
{
  "expected_version": 2,
  "reason": "Operator requested reauthentication."
}
```

It revokes existing sessions and increments the same user administration version without suspending the account. Subsequent legitimate login is allowed. Responses include `revoked_sessions`.

Allowlisted administrators are protected from suspension or session revocation through this API, including self-targeted actions; those requests return `409 PROTECTED_ADMIN`. Administrator identity changes remain a deployment/incident operation. Operators can use ordinary logout to revoke their own current session.

## Monitoring and audit

Stats report counts, not a misleading sum of base-unit amounts across unrelated reward tokens. Indexer state reports its cursor, observed confirmed head, heartbeat, halt reason, and the same freshness/lag policy used by readiness. Job monitoring is read-only. This module does not provide an unsafe generic SQL console, cursor reset, seed regeneration, eligibility override, or automatic failed-job retry.

Administrative actions append `ADMIN_CAMPAIGN_MODERATED`, `ADMIN_USER_SUSPENSION_CHANGED`, or `ADMIN_USER_SESSIONS_REVOKED` to immutable audit history, including actor, target, reason, and resulting version. Retries with the same idempotency key/payload return the original response and do not create another administrative action.
